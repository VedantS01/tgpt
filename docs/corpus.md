# The model corpus — what's in it and why

The spec for this project asks the model to train on **code plus several
high-quality content sources**, all openly available: open code datasets, GitHub,
StackOverflow and similar, Medium-style web writing, research papers, Wikipedia,
wikiHow, and instruction manuals.

`tgpt/corpus.py` is that list made executable. Each source is one row — where it
comes from, how many bytes to take, how to turn a record into a document — so
adding a source is one row and changing the mixture is one number.

```bash
python -m scripts.fetch_corpus --list          # show the mixture
python -m scripts.fetch_corpus                 # fetch it (~2.3 GB)
python -m scripts.fetch_corpus --total-mb 400  # same proportions, smaller
```

Ten programming languages, because the tokenizer's spec only names three but a
model that has seen Go and Ruby generalizes better on the three it is graded on.

Through the M1b 32k tokenizer this is **609.3M tokens** — compute-optimal under
Chinchilla for a 30.5M-parameter model, so the 10.6M tiny config trains at ~57
tokens per parameter. The previous 139 MB corpus was 37.8M tokens, optimal for
1.9M parameters, which is what motivated the rebuild.

## Availability is the hard part, not bandwidth

Datasets rot, and the failure modes are unhelpfully varied. Everything in the
table above was probed before being written into the registry. What didn't
survive:

| source | why not |
|---|---|
| `bigcode/the-stack`, `bigcode/starcoderdata`, `nampdn-ai/tiny-codes` | gated — need an authenticated token |
| `armanc/scientific_papers`, `codeparrot/github-code`, `Fsoft-AIC/the-vault-function` | script-based datasets, which `datasets` 5.0 removed entirely |
| `HuggingFaceH4/stack-exchange-preferences` | ships raw `<p>` HTML; `donfu/oa-stackexchange` is the same content already cleaned |
| `ccdv/arxiv-summarization` | **see below** |

**Research papers are the one spec item deliberately dropped.** The only openly
available full-text arXiv corpus is lowercased with LaTeX stripped to `@xcite`
markers:

```
additive models @xcite provide an important family of models for semiparametric
regression or classification . some reasons for the success of additive models
```

Requirement 7 says the model is case-sensitive. Feeding it 70 MB of caseless,
punctuation-mangled text teaches it that sentences sometimes just don't
capitalize — a cost paid on every other source. Academic register is covered by
`openstax` and `khanacademy` instead, which are properly cased.

C++ has the same problem for the opposite reason: no open C++ dataset survives
the gating and script issues, so C++ comes from **24 library release tarballs**
straight off GitHub — header-only template libraries, macro-heavy test
frameworks, and plain implementation code, chosen for stylistic spread.

## Two honest caveats

**Some of the instructional text is synthetic.** `wikihow`, `openstax` and
`khanacademy` come from HuggingFace's Cosmopedia, which is generated by a model
in the style of those sources rather than scraped from them. Real wikiHow is not
openly redistributable. Synthetic text is clean and on-topic, but it is also
smoother and less varied than the real thing, and a model trained on it inherits
whatever the generating model believed. It is 310 MB of 2,300 MB, and `web_edu`
(real, filtered web text) and `wikipedia` are both larger.

**Held-out slices are per source, not global.** The first ~1 MB of every source
is diverted to `data/heldout/` and never trained on, which is what makes the
bytes-per-token numbers meaningful. It also means the held-out set is the *first*
megabyte rather than a random sample — fine for measuring compression, not a
substitute for the shuffled validation split that `prepare` builds.

## Design notes

**Streaming, budgeted, resumable.** Sources are streamed, so corpus size is set
by the budget rather than by the dataset — `codeparrot-clean` is ~50 GB and
`fineweb-edu` ~27 GB, and we take 400 MB and 190 MB. A source already at its
budget is skipped on re-run, because a 2 GB fetch should not restart from zero
because source 14 timed out. Sources are fetched concurrently; the work is
network latency, not CPU.

**Failures are per source.** A dataset that disappears or 500s is logged and
skipped, and the run continues. The alternative — one bad source aborting an
hour of downloading — is how you end up with no corpus at all.

**Documents, not bytes.** Every source writes documents separated by `DOC_SEP`
(a NUL byte), so the data pipeline can put an EOS token at each boundary and keep
whole documents on one side of the train/val split. See
[`docs/data-pipeline.md`](data-pipeline.md).

## Scaling it

`--total-mb` rescales every source proportionally, so the mixture is
independent of the size. The budgets in `tgpt/corpus.py` are relative weights
that happen to sum to 2,400.

This corpus is sized for a laptop with limited free disk. The sources it draws
from hold hundreds of gigabytes; raising `--total-mb` is the only change needed,
until the disk or the patience runs out.
